# Ordered application modules

Cage executes `modules` in declaration order. Prefix foundation selection, one Wine prefix initialization or qualified CFW adoption, launch configuration, Linux state capture, and artifact sealing are explicit lifecycle operations outside that list. `build/build-plan.json` is the executable operation list: `build/run.sh`, the execution graph, operation provenance, and step evidence refer to its ordered IDs. A failed build records its operation ID in `logs/failed-operation`.

## Inputs and paths

| Path | Meaning |
| --- | --- |
| `sources/setup.msi` | Workspace input, read-only in the build at `/workspace/sources/setup.msi` |
| `/work/unpacked/setup.exe` | Temporary build state, discarded after the build |
| `/etc/vendor-app/config` | Linux application state, captured only when a script declares it in `outputs` or an extract module targets it |
| `C:/Program Files/App/file` | Active Wine prefix `drive_c`; file destinations resolve there |
| `D:/setup.exe` | Explicit, currently mounted ISO media drive; never inferred from an ISO |

Workspace file inputs are audited; SHA-256 is checked when declared. `install`, `files`, registry file imports, script files, ISO, extraction, and DLL deployment use the same source verification pass. A media drive input is bound to the preceding named mount operation. Sources should be immutable and include a SHA-256 when available.

`install` accepts `source`, optional `installer: exe|msi`, `args` (list), `workingDirectory`, `environment`, `timeout` (seconds), `expectedExitCodes` (shell exit codes 0–255), and `sha256`. Only `.exe` and `.msi` infer an installer. MSI defaults to `/qn /norestart` if `args` is omitted; EXE has no invented silent flags. `exe`, `msi`, and `silentArgs` are removed from the public schema. Chocolatey remains a separate package manager module, with `packages: [name]`; old `install.packages` is accepted for existing v0 recipes. Its verified CFW foundation runs once before modules; each package action runs at its declared position. The final package evidence covers all requested packages, and each operation keeps its own evidence file.

`script` accepts exactly one of `run` or `file`, plus `shell: /bin/bash|/bin/sh`, `workingDirectory`, string `environment`, positive `timeout`, `user: root`, and nonempty `outputs`. It is an explicitly unsafe escape hatch. `outputs` must name absolute application-owned Linux paths, such as `/etc/vendor-app` or `/opt/vendor-app`. Shell commands run as root during the ordered build; Wine and application operations continue to run as the `abc` application user. The selected runtime image must advertise `root-build-operations=v1`, so older images fail before execution. That capability is part of a newly built runtime identity and needs its normal qualification; the pinned CFW producer image is not modified. At the end, Cage copies the *resulting files* into a deterministic `linux-state.tar` with file modes and owners, checks its contents, and seals its hash against the immutable base image digest. It does not rerun scripts at export. Undeclared container filesystem changes are discarded; protected Shell/runtime locations, including `/init`, `/usr`, and Cage's lifecycle paths, cannot be declared as outputs. A recipe requiring changes to those components needs a separately qualified derived runtime. CFW recipes continue to reject arbitrary script, registry, extraction, and DLL mutations of the prepared foundation.

Normal `cage run` constructs and caches a derived application runtime image from the sealed Linux snapshot when needed. OCI export uses the same snapshot layer over the pinned base image, plus the built Windows prefix bundle and launch contract. `RUN rm -rf` on declared outputs followed by `ADD linux-state.tar /` replaces their complete final trees, including removals within a declared directory. The derived image tag hashes the immutable base reference and the deterministic archive; `metadata/linux-state.json` binds it to the bundle. OCI export may additionally add graphics-specific labels and bundle metadata. Pelagian Shell `/init` remains inherited from the qualified base.

`install.expectedExitCodes` matches every result, including zero; a missing zero rejects a successful process. A hashed media installer resolves through the active drive mapping and verifies the actual mounted file immediately before Wine starts. Traversal, missing files, and linked paths fail the install operation.

## Registry, DLLs, checks

`registry` accepts exactly one of `file` (optional `sha256`) or `changes`. Structured `set`, `deleteValue`, and `deleteKey` compile into a `.reg` import. Set supports `string`, `expandString`, `dword`, `qword`, and hex `binary`; omitted `name` selects the unnamed default value. Keys must start with `HKCU` or `HKLM`. The operation records the active prefix and application Wine user. Explicit 32/64 view selection and alternate users are rejected until Wine-specific behavior is qualified; use the default view. File imports are declared verified inputs.

`dll` has independent `install` and `overrides` operations. Installation requires a source, SHA-256, and explicit `system32` or `syswow64` target. Loader policies accept `native`, `builtin`, both orders, or `disabled`. No DLL downloads occur. Optional `evidence` carries an ID, observed failure, artifact path, and tested runtime identity into the operation record. Global `compatibility.dllPolicy` remains a launch policy for existing v0 recipes; migrate build-time mutations to ordered `dll`. `check` supports a file existence/hash assertion or an explicit command/exit-code assertion at its recipe position. Command checks are marked unsafe. Final artifact verification still runs independently.

Global `compatibility.dllPolicy` is launch-only. Build setup clears inherited `WINEDLLOVERRIDES` so ordered `dll` registry overrides affect later build operations. At launch, global policy takes precedence through the environment even when it differs from the prefix registry. Move build-time policy into ordered `dll` modules; explicit per-operation environment can override registry loader behavior for that operation. `system32` is the 64-bit directory in win64 prefixes; `syswow64` is the 32-bit directory and is rejected for win32 prefixes. Application-local DLL deployment and binary architecture inspection are not yet supported.

## ISO and extraction

`iso` is a named resource. `mount` requires `id`, ISO `source`, `drive: D` (or another D–Y letter), and `mountPath` to an operator-mounted, read-only host directory inside the workspace. Cage verifies that the host path is an actual read-only mountpoint, exposes it through the read-only workspace bind, maps it to a Wine CD-ROM drive, and records the `host-mounted-read-only` backend. The ISO file is separately hash verified when `sha256` is declared. The operator is responsible for proving that the mountpoint presents *that exact ISO*; Cage currently cannot authenticate this relationship. Missing mount support fails before container execution. No loop mount, privilege escalation, or implicit extraction fallback exists. `unmount` names the resource; unmatched release and use of inactive drive letters fail compilation. Outstanding media are released before sealing. Container failure discards its temporary prefix and mount mapping. Build-only mappings do not enter the bundle. Runtime media needs a future explicit runtime dependency.

`extract` takes `source`, `target`, optional `sha256`, and `maxBytes`. It accepts tested ZIP and TAR variants through Python's archive libraries. ISO requires an explicit `backend: bsdtar|7z` available in the build image, and otherwise fails clearly. The chosen backend is recorded in the plan. The shared safe media extractor rejects traversal and links, checks quotas, and requires an empty target. `/work/...` is temporary; an application-owned target outside `/work` is captured in the final Linux image. Extraction is a separate operation from mounting.

Disc A completing, unmounting, then mounting disc B for a *new* installer fits sequential modules. An installer already running and prompting for disc 2 needs a future explicit media-swap or interactive installer mechanism.

## CFW and private-feed follow-up

Distinguish producer-owned CFW foundation state from application-specific registry, DLL, and shim operations. A future recipe should be able to install a Chocolatey application, deploy a Pelagian shim, configure its registry, and verify it without invalidating the qualified foundation. Keep the current protections until that boundary is implemented. A private feed needs its own authenticated, verifiable package receipts; the public Chocolatey community-feed mechanism cannot simply be disabled. Shim packaging should include application-local deployment, binary architecture inspection, signed/versioned artifacts, paired Linux dependencies, evidence, and private feed delivery.

## Deliberately deferred

A genuine Containerfile fragment would need a builder that executes `RUN --mount`, `ENV`, `LABEL`, and `COPY` at the specified recipe position and checks protected runtime changes before claiming qualification. A final-export-only fragment changes semantics, so `containerfile` remains unsupported. Explicit registry views/users, additional rootless ISO/FUSE backends, in-process disc swaps, and package version pinning require targeted integration work.

The future compatibility catalogue should hold evidence-backed fixes that expand *in place* into ordinary registry/DLL/check/install operations, never another executor. Its evidence should identify application/version, failure category and diagnostic artifact, tested Cage and Wine runtime identities, selected ordered operations, checks, result, and limitations. A separately versioned shim artifact should record its source/build provenance, architecture, interfaces, hash, destination, override policy, tested runtimes, and evidence. Wine source patches belong to runtime construction, requalification, and a new immutable runtime digest; an application recipe cannot mutate Wine itself or retain stale qualification metadata. No application recipe `wine-patch` module exists.
